# 部署与维护

项目：`/opt/tg-auto-ad`。机器人：@KunKunGuangGaoBot。所有业务和管理在Telegram私聊进行，无网页后台。程序使用官方Bot API长轮询，独立Worker与PostgreSQL16持久化队列。

## 环境与文件

- Ubuntu24.04，Python3.12，独立`.venv`；依赖固定于`requirements.txt`。
- 独立系统账号/数据库角色`adbot`，生产数据库`auto_ad`，UNIX socket peer认证。测试数据库`auto_ad_test`、备份恢复核验数据库`auto_ad_restore_check`均不参与生产。
- `.env`属主`adbot:adbot`、权限600；`.env.example`不含真实Token。修改Token后重启两个服务，禁止把密钥写入工单/日志/公开压缩包。
- 源码/迁移644、目录755；`data`、`logs`、`backups`目录700。数据库只允许本机访问，不需要开放公网数据库端口。
- `migrations`按文件名应用，已执行记录保存在`schema_migrations`。禁止修改已经上线的迁移；新增迁移文件。

## 新服务器安装

以下适用于全新Ubuntu24.04；本机已完成，勿重复初始化生产库。先将源码放入相同目录，再安装依赖：

```bash
apt-get update
apt-get install -y postgresql postgresql-contrib python3-venv
useradd --system --home-dir /opt/tg-auto-ad --no-create-home --shell /usr/sbin/nologin adbot
cd /opt/tg-auto-ad
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
runuser -u postgres -- createuser --login adbot
runuser -u postgres -- createdb --owner=adbot auto_ad
runuser -u postgres -- psql -c "ALTER ROLE adbot SET timezone TO 'UTC';"
install -o adbot -g adbot -m 600 .env.example .env
install -d -o adbot -g adbot -m 700 data logs backups
```

用受控编辑器填写`.env`真实Token，核对管理员和DSN；本机socket认证要求操作系统用户和SQL角色同名。测试需另建`auto_ad_test`空库归adbot，生产运行不依赖测试库。源码和迁移须允许adbot读取（文件644、目录755）。

```bash
install -m 644 deploy/tg-auto-ad-bot.service /etc/systemd/system/tg-auto-ad-bot.service
install -m 644 deploy/tg-auto-ad-worker.service /etc/systemd/system/tg-auto-ad-worker.service
systemctl daemon-reload
systemctl enable --now tg-auto-ad-worker.service tg-auto-ad-bot.service
```

首次启动自动执行迁移。不需要安装或启动Web服务，也不依赖Redis/MySQL。更改部署目录时必须同步修改systemd中的WorkingDirectory、EnvironmentFile、ExecStart、ReadWritePaths及虚拟环境。

## 服务管理

```bash
systemctl status tg-auto-ad-bot.service tg-auto-ad-worker.service
systemctl restart tg-auto-ad-bot.service tg-auto-ad-worker.service
systemctl stop tg-auto-ad-bot.service tg-auto-ad-worker.service
journalctl -u tg-auto-ad-bot.service -u tg-auto-ad-worker.service -n 100 --no-pager
journalctl -u tg-auto-ad-worker.service -f
```

两个服务均开机启动、失败自动重启；数据库advisory lock阻止同角色双实例。接收服务负责持久化updates和用户交互，Worker负责轮播、即时来源、广播和测试删除。新建任务默认为草稿，保存后必须确认启动。网络结果未知不会自动重发，须在任务/广播详情核对。

每次接收服务启动会向管理员100000001、100000002各尝试发送一条启动通知；不会向所有用户或频道群组自动发送广告。已经明确启动的任务及广播按数据库状态继续；残留在途请求进入UNKNOWN。Worker异常会尝试通知管理员，连续异常退出后由systemd重启。

## 健康检查

```bash
cd /opt/tg-auto-ad
runuser -u adbot -- .venv/bin/python scripts/health.py
```

输出接收/Worker心跳、待处理和错误updates、UNKNOWN数量、运行任务、数据库大小和迁移。接收心跳100秒以内、Worker120秒以内返回0，否则返回1。启动初次长轮询、长时间429冷却或大批次处理可能造成暂时超时，应结合journal和队列判断。此工具不会自动创建定时任务或对外监控告警；可接入已有监控系统。

## SQL备份与恢复

```bash
cd /opt/tg-auto-ad
runuser -u adbot -- .venv/bin/python scripts/backup.py
```

工具生成`backups/auto_ad-UTC时间.dump`，使用pg_dump一致性快照和自定义格式，并用pg_restore --list校验目录。备份包括永久内容、任务状态、消息/审计日志和配置；媒体保存Telegram file_id，非本机视频/图片原件。备份文件600，不自动轮换或删除。应定期复制到受控异机，另行保存私有`.env`和服务定义。当前不设置定时备份计划。

恢复先使用**全新空库**，恢复工具拒绝覆盖当前DATABASE_URL对应数据库及任何已有表：

```bash
runuser -u postgres -- createdb --owner=adbot auto_ad_recovery
runuser -u adbot -- .venv/bin/python scripts/restore.py backups/所选备份.dump --target auto_ad_recovery
runuser -u adbot -- psql -d auto_ad_recovery -c 'SELECT count(*) FROM schema_migrations;'
```

核验内容后，停止两个服务，备份当前库，再把`.env`的DATABASE_URL库名切到恢复库，启动服务并运行health。恢复较旧备份时，Telegram外部消息状态无法倒退；可能存在已发但备份未记的消息，必须核对相关任务/广播，避免重复发送。回滚源码也需要兼容SQL迁移；不执行破坏性降级脚本。

## Telegram 连接异常排查

2026-11-08 排查确认：服务进程仍存活时，发送连接也可能出现 `ConnectTimeout` 或 TLS `Hostname mismatch`。使用 `systemctl status` 查看两个服务，并结合健康检查、journal、任务失败记录和实际 API 权限判断，不能仅凭进程存在认定业务正常。

私有 `.env` 提供可选 `TELEGRAM_API_IPS`，逗号分隔、由部署者自行核实的 `api.telegram.org` 地址（该域名由 Telegram 运营，地址会变动，请勿照抄任何示例）。填写后应先用独立 DoH 或权威解析确认，并通过正常主机名 TLS 验证。本配置仅影响本程序进程内的精确域名解析；不改系统 DNS/hosts，不更换 API URL，不关闭证书验证。地址失效时应重新核实或清空此配置，然后重启接收和 Worker 服务。

`Chat not found` / `Member list is inaccessible` 还可能是机器人已被目标移除。任务开启“失败跳过”后会继续推进并保留失败记录；调度批次 `COMPLETED` 不代表所有投递成功，需查看投递 `SUCCESS` / `FAILED` 统计。重新将机器人加入目标并授予管理员和发帖权限，重新绑定后，手动恢复已暂停任务；不要把已完成失败批次全部重放到频道。

## BotFather与平台设置

1. `/mybots`选择机器人；Token仅配置于私有`.env`。
2. 程序自动设置`/start`、`/help`、`/cancel`及管理员专用`/admin`命令、菜单按钮、机器人简介。
3. 本项目不需要Webhook域名或HTTPS入口；不要同时在其他地方运行相同Token的getUpdates或Webhook消费者。
4. 目标和来源首次绑定要求机器人与操作者均为管理员；频道bot需要发帖权限。群组bot管理员可接收来源消息，隐私模式开关不替代管理员授权。
5. 会员图标资格按Telegram实际接口执行；所有菜单类别的图标均从真实图标集核验，管理员发送的custom emoji实体直接保留，不要求手填ID。频道与不同客户端显示仍需各场景实测。

```bash
cd /opt/tg-auto-ad
runuser -u adbot -- env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -p no:cacheprovider -q
```

SQL测试仅连接`auto_ad_test`并生成随机schema，结束清理；Bot为假对象，不会对用户广播。`scripts/live_smoke.py`为**真实管理员私聊实发工具**，会发送菜单及彩色按钮/会员表情验收消息。`scripts/live_worker_smoke.py`在测试库随机schema向一位配置管理员实发轮播删旧和单接收者广播/进度，结束清理；仅为此私聊诊断替换目标管理员检查，不能据此认定频道/群组权限验收完成。两个脚本均不能作为普通自动测试重复运行。

免费发送共享全局约20次/秒、同频道/私聊约1.05秒间隔、同群约3.1秒间隔；429使用Telegram实际retry_after全局冷却。10000目标一轮仅计算全局发送下限就约8分20秒，删除旧消息、权限查询、媒体、同群限制和网络会增加时间；最小1分钟设置不代表10000目标能每分钟发完一轮。轮播下一轮从本批完成后计算间隔，不积压补发所有错过轮次。

长期永久保留需要监测磁盘、数据库大小、WAL、备份数量及查询时间。当前未自动清理业务内容和日志，磁盘满会影响服务。相册作为后续扩展，当前按单条文字/图片/视频/动画/文档处理；不支持用户账号Session、任意历史遍历或绕过保护内容。

## 收费配置与恢复

收费数据库迁移为 `004_billing.sql`；管理员通过机器人“管理员 → 收费管理 → 收款配置”录入 OKPay 商户号与支付密钥，不能用普通系统配置保存支付密钥。服务端 `.env` 必须有独立 `BILLING_ENCRYPTION_KEY`，可用项目虚拟环境执行 `python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'` 生成。只在首次配置前生成一次；正式配置后不得随意替换，否则历史支付凭据无法解密。

SQL 备份仅包含加密凭据，恢复时必须同时安全保管原加密密钥与服务私有配置。支付密钥轮换保留旧加密凭据用于历史订单查单；不要删除凭据或将其导出到日志、源码包。管理员普通私聊文本在收件箱中仅保留脱敏占位，原文处理期间只在内存，重启后未完成的敏感输入需重新发送。

Worker 有独立支付查单循环，不使用外部 Web 回调或额外 TCP 监听。待处理订单的查单采用订单锁、最少30秒退避与有限并发；创建请求超时不会自动重建订单。结果不明时保留原订单，禁止通过重新调用创建接口来恢复链接。

链接丢失且仅为精确链接校验错误的原单，可在双次签名查单均确认同一未付款订单后重建官方固定收款链接；其他审核状态不自动解除。付款入账仍须金额、币种、商户及订单完整匹配，唯一权益记录与订单 PAID 在同一事务提交。未付款链接恢复不等于已付款验收。

完整商品、额度、到期和管理员操作规则见[收费使用说明](收费使用说明.md)，本次测试与上线范围见[收费升级报告](收费升级报告.md)。
